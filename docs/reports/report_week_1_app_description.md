# Система IT-поддержки Support Desk

Приложение организует обработку обращений в IT-поддержку. Пользователь регистрируется, создаёт заявку, выбирает категорию и приоритет, отслеживает статус и переписывается с операторами. Оператор видит общую очередь, назначает исполнителя, отвечает на сообщения, меняет статус и поддерживает справочник категорий. Интерфейс и README написаны на английском языке.

Пользователь может читать только свои заявки; редактировать и удалять их — только в состоянии `open`. Оператор может работать со всеми заявками. Комментарий редактирует только его автор; удаляет автор либо оператор. У закрытой заявки обсуждение доступно только для чтения, пока оператор не откроет её снова. Управление заявкой основано на действиях: оператор забирает заявку из очереди, назначает исполнителя через поиск, разрешает её с обязательным сообщением. Автор разрешённой заявки подтверждает исправление (закрытие) либо описывает оставшуюся проблему (возврат в работу). Оператор может открыть разрешённую/закрытую заявку снова с обязательной причиной. Сообщение и переход состояния сохраняются в одной транзакции. Произвольное изменение статуса и исполнителя через PATCH запрещено. Роль выбирается при регистрации и впоследствии не изменяется. Для регистрации оператора нужен код приглашения из серверной конфигурации; пустой код отключает такую регистрацию.

## Стек и устройство

- Go 1.27, Gin.
- PostgreSQL: база данных.
- Bun, PostgreSQL dialect и pgdriver поверх `database/sql`: параметризованные запросы, пул соединений и транзакции.
- Goose v3: версионированные SQL-миграции, встроенные в бинарный файл.
- React, TypeScript, Vite, React Router, TanStack Query, CSS Modules: интерфейс пользователя и оператора.
- Docker Compose: PostgreSQL, отдельные процессы миграции/заполнения категорий, приложение.
- Go tests с race detector, Vitest/Testing Library и Playwright: проверки правил доступа, конкурентных изменений и пользовательских сценариев.

Обработчик HTTP проверяет JSON и идентифицирует сессию; сервис принимает решения о правах и состоянии заявки; репозиторий выполняет операции с PostgreSQL. Исходники сервера и Go-модуль находятся в `../../backend`, исходники React и npm-манифесты — в `frontend/`. Встраивание ресурсов реализовано исключительно в `backend/internal/staticui`: сборка копирует туда результат Vite, затем Go встраивает его в бинарный файл. Во фронтенде нет Go-файлов. Фронтенд использует относительные адреса `/api/v1`, поэтому в production API и интерфейс доступны с одного origin. Фильтры списка сохраняются в URL. В production образе один бинарный файл содержит миграции и собранный фронтенд; Node требуется только при сборке и разработке.

## Основные сущности

| Сущность                 | Данные и назначение                                                                                                    |
|--------------------------|------------------------------------------------------------------------------------------------------------------------|
| Пользователь (`users`)   | Имя, уникальный без учёта регистра email, bcrypt-хеш пароля, роль user/operator, временные метки.                      |
| Сессия (`sessions`)      | SHA-256-хеш случайного токена, пользователь и срок действия. Исходный токен хранится только в HttpOnly cookie клиента. |
| Категория (`categories`) | Уникальное без учёта регистра имя, описание и временные метки.                                                         |
| Заявка (`tickets`)       | Заголовок, описание, категория, приоритет, статус, автор, необязательный оператор, временные метки.                    |
| Комментарий (`comments`) | Заявка, автор, текст и временные метки создания/изменения.                                                             |

Приоритеты: low, medium, high, urgent. Статусы: open, in_progress, resolved, closed. СУБД проверяет внешние ключи, обязательность полей, длину и допустимые значения. Удаление заявки каскадно удаляет комментарии. Удаление используемой категории блокируется с HTTP 409. Списки содержат пагинацию; результаты и количество отбираются с одинаковыми ограничениями видимости в едином снимке транзакции.

Изменение заявки и операции с комментариями блокируют строку родительской заявки через `SELECT FOR UPDATE`. Проверка прав и состояния выполняется после получения блокировки и до завершения транзакции. Таким образом, одновременное закрытие заявки не позволяет пользователю изменить уже недоступные данные.

## 12 факторов

| Фактор                               | Реализация и проверяемое свидетельство                                                                                                                                                                                                                                                    |
|--------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 1. Кодовая база                      | Все исходники, миграции, тесты и описание развёртывания находятся в одном дереве проекта. `../../.gitignore` исключает секреты и результаты сборки. Для приложения инициализирован один Git-репозиторий. Изменения доступны для проверки; коммиты и теги связывают утверждённый код с релизами. |
| 2. Зависимости                       | Go-зависимости фиксируются `go.mod`/`go.sum`, frontend — точными версиями в `package.json` и `package-lock.json`. Dockerfile использует `npm ci`, `go mod download` и фиксированные версии базовых образов. Не требуется неявная установка библиотек на хосте.                            |
| 3. Конфигурация                      | DSN, порт, уровень логов, пул, таймауты, срок сессии, Secure cookie и приглашение задаются переменными окружения. `../../.env.example` содержит только заменяемые значения, `.env` не включается в архив.                                                                                       |
| 4. Сторонние службы                  | PostgreSQL подключается через `DATABASE_URL`; база заменяется настройкой без изменения кода. В PostgreSQL хранятся и пользовательские данные, и сессии.                                                                                                                                   |
| 5. Сборка, релиз, выполнение         | Многоэтапная сборка создаёт frontend и Go-бинарный файл. Образ связывается с `VERSION`, содержит миграции и метаданные. Compose выполняет миграции отдельным процессом до запуска сервиса. Runtime не компилирует исходники.                                                              |
| 6. Процессы                          | Приложение не держит авторитетное состояние в памяти или локальных файлах. Перезапуск процесса сохраняет заявки, обсуждения, аккаунты и сессии. Кэш браузера очищается при выходе и истечении сессии.                                                                                     |
| 7. Привязка портов                   | Приложение самостоятельно слушает HTTP-порт из `PORT`. Статические ресурсы и API обслуживает один Go HTTP-сервер; отдельный веб-сервер не требуется.                                                                                                                                      |
| 8. Параллелизм                       | Одинаковые экземпляры используют общую PostgreSQL. Сессия распознаётся любым экземпляром, привязка клиента к процессу не требуется. Транзакции и блокировки согласуют конкурентные изменения.                                                                                             |
| 9. Утилизируемость                   | На SIGTERM/SIGINT readiness становится отрицательной, сервер завершает активные запросы с ограниченным временем ожидания. Есть таймауты запросов/БД, recovery и отдельные `/healthz`, `/readyz`. Запуск не выполняет сборку и не создаёт аккаунты.                                        |
| 10. Сходство разработки и production | В разработке и тестах используется PostgreSQL, как и в production. Один production образ запускается локально через Compose. Vite proxy нужен только для удобства разработки фронтенда.                                                                                                   |
| 11. Логи                             | Структурированные JSON-события выводятся в stdout: идентификатор запроса, метод, путь, HTTP-статус и длительность. Тела запросов, пароли, cookie и коды приглашения не журналируются. Сбор логов выполняет внешнее окружение.                                                             |
| 12. Административные процессы        | `support migrate`, `support seed`, `support cleanup-sessions` используют тот же образ и окружение. Миграции и заполнение категорий повторяемы; регистрация аккаунтов выполняется через интерфейс, отдельные встроенные аккаунты отсутствуют.                                              |

## Запуск и проверка

Скопировать `../../.env.example` в `.env`, заменить пароль PostgreSQL и приглашение, выполнить `docker compose up --build -d` и открыть `http://localhost:8080`. Подробные команды разработки, административных процессов, проверок и сборки архива приведены в [README.md](../../README.md). Контракт API находится в [docs/openapi.json](../openapi.json).

Интеграционные тесты с PostgreSQL проверяют регистрацию обоих типов аккаунтов, приглашения, валидацию паролей, сессии, запрет cross-origin изменений, CRUD, изоляцию пользователей, совпадение фильтров и количества результатов, назначение оператора, ограничения закрытой заявки, удаление используемой категории и каскадное удаление. Конкурентные тесты удерживают блокировку строки заявки при её закрытии и проверяют, что изменение заявки, создание, редактирование и удаление комментария ждут эту блокировку и затем отклоняются. Playwright выполняет сценарий подачи заявки и ответа оператора, проверяет второго пользователя, обновление страницы, фильтры, выход, справочник категорий и пагинацию.
