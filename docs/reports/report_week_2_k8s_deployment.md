# Развёртывание Support Desk в Kubernetes

Support Desk организует обработку обращений в IT-поддержку. Пользователь регистрируется, создаёт заявку, выбирает категорию и приоритет, отслеживает статус и переписывается с операторами. Оператор работает с общей очередью, назначает исполнителя, отвечает на сообщения и меняет состояние заявки.

Для развёртывания подготовлены манифесты однонодового Kubernetes-кластера Minikube. Приложение и PostgreSQL запускаются в пространстве имён `support-desk`. Манифесты и подробные команды находятся в [k8s/README.md](../../k8s/README.md).

## Стек и устройство

- Go, Gin: HTTP API и раздача статических файлов интерфейса.
- React, TypeScript, Vite: клиент пользователя и оператора.
- PostgreSQL 18: данные пользователей, сессий, категорий, заявок и комментариев.
- Bun и `database/sql`: запросы, пул соединений и транзакции.
- Goose: SQL-миграции, встроенные в исполняемый файл.
- Docker: сборка образа приложения.
- Minikube, kubectl: локальный Kubernetes-кластер и управление ресурсами.

[Dockerfile](../../Dockerfile) использует многоэтапную сборку. Сначала собирается frontend, затем его файлы встраиваются в Go-бинарный файл. В конечный образ Alpine переносится исполняемый файл `/support`. Один контейнер обслуживает интерфейс и API на порту 8080; Node нужен только во время сборки. Образ `support-desk:k8s-v1` используется сервером, миграциями и заполнением начальных категорий. Для PostgreSQL используется тот же закреплённый digest образа, что и в Docker Compose.

## Абстракции Kubernetes

| Абстракция            | Реализация и назначение                                                                                                                         |
|-----------------------|-------------------------------------------------------------------------------------------------------------------------------------------------|
| Namespace             | `support-desk` объединяет ресурсы приложения и отделяет их от учебных нагрузок.                                                                 |
| Deployment            | `support-app` поддерживает заданное число экземпляров приложения и обновляет их. `postgres` поддерживает один экземпляр базы данных.            |
| ReplicaSet            | Создаётся Deployment автоматически и поддерживает число Pod соответствующей версии шаблона.                                                     |
| Pod                   | Запускает контейнер приложения, PostgreSQL или административной команды. Создаётся контроллером Deployment либо Job.                            |
| Service               | `support-app` предоставляет внутренний адрес приложения на порту 8080, `postgres` — адрес базы данных на порту 5432. Оба имеют тип `ClusterIP`. |
| PersistentVolumeClaim | `postgres-data` запрашивает 1 GiB постоянного хранилища через StorageClass по умолчанию. Том монтируется в `/var/lib/postgresql`.               |
| ConfigMap             | `support-config` хранит порт, уровень логов, размер пула, тайм-ауты, срок сессии, режим cookie, имя пользователя и базы данных.                 |
| Secret                | `support-secret` хранит пароль PostgreSQL, `DATABASE_URL` и код приглашения оператора. Значения передаются контейнерам через `secretKeyRef`.    |
| Job                   | `support-migrate` выполняет `/support migrate`; `support-seed` выполняет `/support seed`. После успешного выполнения процессы завершаются.      |

Для приложения задана одна начальная реплика и стратегия `RollingUpdate`: `maxSurge: 1` разрешает один дополнительный Pod во время обновления, `maxUnavailable: 0` сохраняет желаемое количество доступных реплик. Для базы данных задана стратегия `Recreate`, чтобы старый Pod завершался до запуска нового, использующего тот же том. Количество реплик PostgreSQL остаётся равным одному: обычное масштабирование Deployment не настраивает репликацию базы.

PVC сохраняет данные при замене Pod PostgreSQL. Режим `ReadWriteOnce` ограничивает запись одним узлом, а не одним Pod. Удаление PVC или пространства имён может удалить данные, поэтому остановка приложения и удаление хранилища рассматриваются отдельно.

## Взаимодействие сервисов

Браузер получает React-интерфейс и обращается к Go API по относительным адресам `/api/v1`. Интерфейс и API доступны с одного origin. Для демонстрации используется `kubectl port-forward service/support-app 8080:8080`: локальный порт перенаправляется в один выбранный Pod приложения.

Внутри кластера Service `support-app` выбирает готовые Pod по метке `app: support-app`. Приложение подключается к PostgreSQL по адресу `postgres:5432`; имя `postgres` разрешается через DNS Kubernetes. Service базы выбирает Pod с меткой `app: postgres`. Строка подключения имеет вид `postgres://support:<пароль>@postgres:5432/support?sslmode=disable` и поступает из Secret. Адрес конкретного Pod базы может меняться, но имя Service остаётся прежним.

Jobs миграции и заполнения категорий подключаются к той же базе через тот же Service. Все экземпляры HTTP-сервера используют общие данные и сессии PostgreSQL. Авторизация не привязана к памяти отдельного экземпляра, поэтому увеличение числа реплик не требует закрепления пользователя за определённым Pod.

## Конфигурация и жизненный цикл

Приложение получает обычные параметры из ConfigMap через `envFrom`, а чувствительные значения — из Secret. Kubernetes создаёт переменные окружения, которые Go-код читает при запуске. Изменение ConfigMap или Secret требует перезапуска Pod для обновления этих переменных. Комплект содержит демонстрационные секреты для локальной работы; реальные значения должны передаваться отдельно от исходного кода.

Startup и liveness приложения используют `/healthz`, readiness — `/readyz`. Первый endpoint проверяет ответ HTTP-сервера, второй — доступность базы данных и состояние завершения сервера. При недоступности базы readiness исключает экземпляр из готовых адресатов Service, не используя сбой PostgreSQL как причину перезапуска HTTP-сервера. Для PostgreSQL startup и readiness выполняют `pg_isready` через TCP localhost.

Для приложения и Jobs заданы запросы и ограничения CPU и памяти. Контейнеры работают от пользователя 65532, с файловой системой только для чтения, без дополнительных Linux capabilities и повышения привилегий. Автоматическое монтирование токена ServiceAccount отключено: процессам не нужен доступ к API Kubernetes.

При SIGTERM сервер прекращает сообщать о готовности и завершает активные запросы. Тайм-аут приложения составляет 15 секунд, а Kubernetes предоставляет 20 секунд до принудительного завершения. Jobs ограничены общим временем 120 секунд и двумя повторными попытками; административному процессу предоставляется 60 секунд.

## Запуск и проверка

Команды выполняются из корня проекта. Для сборки внутри Docker-демона Minikube используется следующий порядок:

```sh
minikube start --driver=docker --container-runtime=docker --cpus=2 --memory=4096
kubectl config use-context minikube
eval "$(minikube docker-env)"
docker build --build-arg VERSION=k8s-v1 -t support-desk:k8s-v1 .
minikube image load support-desk:k8s-v1
```

При использовании `docker-env` образ уже доступен в Docker-демоне Minikube; команда загрузки также приведена в соответствии с заданием. Манифесты приложения и Jobs используют `imagePullPolicy: IfNotPresent`.

Развёртывание выполняется последовательно:

1. Создаются Namespace, ConfigMap и Secret.
2. Применяется `postgres.yaml`; ожидается готовность базы данных.
3. Применяется `migrate.yaml`; ожидается состояние Job `Complete`.
4. Применяется `seed.yaml`; ожидается состояние Job `Complete`.
5. Применяется `app.yaml`; ожидается готовность Deployment приложения.

Каждый этап начинается после успешного предыдущего. Сервер не запускает миграции автоматически, а Kubernetes не выводит этот порядок из набора файлов. Последовательность автоматизирована в [k8s/deploy.sh](../../k8s/deploy.sh): скрипт ожидает готовность PostgreSQL, пересоздаёт Jobs миграций и заполнения категорий и запускает приложение после их завершения. При ошибке выполнение прекращается. Запуск после сборки и загрузки образа: `./k8s/deploy.sh`. Полные команды `kubectl apply`, `rollout status` и `wait` приведены в [инструкции запуска](../../k8s/README.md).

Для просмотра ресурсов и демонстрации масштабирования:

```sh
kubectl --context=minikube -n support-desk get pods,deployments,services,jobs,pvc
kubectl --context=minikube -n support-desk scale deployment/support-app --replicas=3
kubectl --context=minikube -n support-desk rollout status deployment/support-app --timeout=180s
kubectl --context=minikube -n support-desk get pods -o wide
```

Ожидаются три готовых Pod приложения и один Pod PostgreSQL на одной ноде Minikube. Успешно завершённые Pod административных Jobs имеют состояние `Completed`. Для доступа к интерфейсу в отдельном терминале выполняется:

```sh
kubectl --context=minikube -n support-desk port-forward service/support-app 8080:8080
```

Интерфейс доступен по адресу http://localhost:8080. Аккаунты создаются через регистрацию; оператор вводит код приглашения из серверной конфигурации.

Скринкаст предыдущей работы хранится в корне рабочего репозитория как `screencast.mp4`; в архив лабораторной по логированию он не включён.
